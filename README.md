# Чат с LLM

## Инструкция по запуску

**В моем окружении для работы чата нужен VPN.** Через него должны идти запросы backend к LLM, поэтому VPN только в браузере не поможет.

Для запуска нужен Docker с Docker Compose. Из корня проекта:

```powershell
cd infra
docker compose up -d --build
```

После запуска открыть [http://localhost:8080](http://localhost:8080), нажать **Получить ключ**, затем **Войти**.

Swagger доступен на [http://localhost:8000/docs](http://localhost:8000/docs).

Если проект уже запущен, применить изменения backend и nginx из директории `infra`:

```powershell
docker compose up -d --build api
docker compose restart nginx
```

## Структура проекта

Весь проект содержится внутри одного Git-репозитория и разделен на три основных модуля: `backend`, `frontend`, `infra`.

### backend

Отвечает за работу с БД и API.

Внутри backend код разделен на слои `repositories`, `services`, `routers`. Основная идея состоит в том, чтобы разделять ответственность за операции с БД, бизнес-логику и маршрутизацию.

- **FastAPI** — фреймворк с поддержкой асинхронности, который позволяет быстро и с большой гибкостью построить веб-приложение. Выбрал его, потому что больше всего опыта с ним.
- **Postgres** — БД для долгосрочного хранения данных, стандартный вариант реляционной БД.
- **LangChain** — фреймворк для работы с LLM. Использую для вызовов API модели, также он позволяет выстраивать удобные пайплайны для генерации ответа.
- **SQLAlchemy** — ORM для работы с БД.

Файлы и директории:

- `database.py` — конфигурация БД и вспомогательные функции для БД.
- `settings.py` — конфигурация проекта через `pydantic-settings`, чтобы валидировать переменные окружения для авторизации и LLM. Настройки БД читаются отдельно в `database.py`.
- `llm_client.py` — конфигурация LLM-клиента через LangChain.
- `main.py` — точка входа в приложение.
- `data/prompts/system_prompt.txt` — системный промпт для LLM.
- `models/` — модели БД.
- `schemas/` — Pydantic-схемы для входных данных и ответов API.
- `repositories/` — модуль для работы с БД.
- `services/` — модуль с бизнес-логикой приложения.
- `routers/` — модуль для работы с маршрутизацией API.
- `Dockerfile` — команды для сборки образа и запуска сервиса `api`.

### frontend

Отвечает за графический интерфейс программы.

- `index.html` — верстка страниц авторизации и чата.
- `styles.css` — стилизация верстки.
- `app.js` — вызовы API на фронтенде, работа с WebSocket и прочая логика.

### infra

Отвечает за запуск и конфигурацию проекта.

- `docker-compose.yml` — описание контейнеров, из которых состоит приложение: БД, API и веб-сервер nginx. Nginx отдает фронтенд и выступает reverse proxy для API.
- `nginx.conf` — конфигурация nginx.

## Как работает авторизация по ключу

По ТЗ требовалось выполнять авторизацию по ключу, который задается в окружении. Я немного изменил подход.

В переменных окружения задается секрет `AUTH_KEY_SECRET`. Backend считает его SHA-256-хеш — это и есть API-ключ, который пользователь получает по кнопке **Получить ключ**. Сам секрет пользователю не передается.

При входе фронтенд отправляет ключ на backend. Backend снова считает хеш своего секрета и сравнивает его с присланным ключом. Если они совпадают, проверка пройдена. Ключ также проверяется в запросе `get_chat_info`, который находит или создает чат.

Если поменять секрет, изменится ключ. Нужно будет получить его заново, и с ним откроется новый чат. Старые сообщения останутся в БД.

Это упрощенное решение для тестового задания. Ключ можно получить со страницы входа, а история и WebSocket доступны по `chat_id` без проверки ключа.

## Как устроена БД

В БД есть две таблицы: сообщения (`messages`) и чаты (`chat_session`). Юзеров мы не регистрируем, чат привязан к API-ключу. Каждое сообщение связано с чатом через `chat_id` и содержит роль автора: `user` или `assistant`.

БД создается при первом запуске контейнера Postgres с пустым volume. Таблицы инициализируются при запуске API через `Base.metadata.create_all()`: отсутствующие таблицы создаются, структура существующих не обновляется.

## Какой провайдер LLM

Использую OpenRouter. В переменной окружения `LLM_MODEL` можно указать другую модель для текстового чата, которая поддерживает используемые параметры. Настройки находятся в `infra/docker-compose.yml`.

На балансе для проверки есть пара баксов. При моем запуске для запросов к OpenRouter нужен VPN.

## Какие изменения можно сделать в перспективе

- Регистрировать пользователей для реальной связки юзер — чаты.
- Сделать нормальную выдачу и хранение API-ключей для пользователя, добавить срок действия и возможность отзыва.
- Добавить миграции БД для хранения версий изменения схемы и возможности отката.
- Использовать tool calling и LangGraph при более сложных пайплайнах работы с контекстом сообщений и LLM.
